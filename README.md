# Smart Home Tech

Мультимодульное приложение для обработки телеметрии умного дома и работы с товарным контуром. Проект объединяет асинхронную обработку событий через Kafka, взаимодействие по gRPC и REST, централизованную конфигурацию и регистрацию сервисов в Eureka.

## Commerce и API Gateway

### Product Service

Хранит категории и карточки товаров. Поддерживает создание, чтение, обновление, поиск и получение товаров по категории; публичные запросы возвращают только активные товары.

### Inventory Service

Хранит общее и зарезервированное количество каждого товара. Позволяет получать и изменять остатки, резервировать товар для заказа и отменять ранее созданный резерв.

### Order Service

Создаёт и хранит заказы. При создании получает актуальные данные о товарах из `product-service` и резервирует остатки через `inventory-service`. Если зависимый сервис временно недоступен, заказ сохраняется в статусе `PENDING_CONFIRMATION`; при ошибке резервирования уже созданные резервы компенсируются.

### API Gateway

Единая внешняя точка входа для товарного контура. Маршрутизирует запросы к товарам, категориям, остаткам и заказам через Eureka, применяет CORS и HTTP Basic-аутентификацию. Публичны чтение каталога и остатков; пользовательские и административные операции защищены ролями `USER` и `ADMIN`.

## Структура проекта

```text
plus-smart-home-tech/
├── telemetry/
│   ├── collector/              # Приём событий и публикация в Kafka
│   ├── aggregator/             # Формирование актуальных снимков состояния хабов
│   ├── analyzer/               # Сценарии автоматизации и отправка команд устройствам
│   └── serialization/
│       ├── avro-schemas/       # Avro-модели событий и снимков
│       ├── avro-serialization/ # Общие сериализаторы и десериализаторы
│       └── proto-schemas/      # Protobuf-контракты gRPC
├── commerce/
│   ├── product-service/        # Каталог товаров и категории
│   ├── inventory-service/      # Остатки и резервирование товаров
│   └── order-service/          # Создание и получение заказов
├── infra/
│   ├── discovery-server/       # Eureka Server
│   ├── config-server/          # Spring Cloud Config Server
│   └── api-gateway/            # Внешняя точка входа товарного контура
├── hub-router/                 # Скрипты запуска тестового роутера хабов
├── docker-compose.yml          # Kafka, PostgreSQL и создание топиков
└── pom.xml                     # Родительский Maven-модуль
```

### Collector

Принимает события датчиков и хабов по HTTP и gRPC. Входные модели преобразуются сначала во внутренние объекты, затем в Avro-сообщения и публикуются в отдельные Kafka-топики.

Разделение mapper-классов для HTTP/Protobuf и Avro позволяет не связывать транспортный формат с форматом хранения событий в Kafka.

### Aggregator

Последовательно читает события датчиков и поддерживает актуальный снимок состояния каждого хаба. После изменения состояния публикует новый снимок в `telemetry.snapshots.v1`.

Consumer работает с отключённым автоматическим подтверждением смещений. Смещения фиксируются после обработки полученной пачки сообщений.

### Analyzer

Обрабатывает два независимых потока:

- события хабов — изменяют состав устройств и сценариев в базе данных;
- снимки датчиков — проверяются на соответствие условиям сохранённых сценариев.

Для событий хабов применяется реестр обработчиков. Тип payload определяет конкретный обработчик, поэтому добавление нового события не требует разрастания одного общего условного блока.

Условия сценария проверяются последовательно. Действия отправляются только тогда, когда выполнены все условия. Команды устройствам передаются в Hub Router по gRPC.

## Хранение данных

Для сервисов, которым требуется постоянное состояние, применяется подход Database per Service:

| Сервис | База данных | Основные данные |
|---|---|---|
| `analyzer` | `telemetry_analyzer` | устройства, сценарии, условия и действия |
| `product-service` | `product_db` | категории и карточки товаров |
| `inventory-service` | `inventory_db` | общее и зарезервированное количество товаров |
| `order-service` | `order_db` | заказы и их позиции |

Схема каждого сервиса находится в его собственном `schema.sql`. Hibernate не создаёт структуру автоматически: при запуске Spring выполняет SQL-инициализацию, а JPA используется для работы с уже созданными таблицами.

Между базами разных сервисов нет внешних ключей. Связь поддерживается через UUID и межсервисные вызовы.

## Транзакции и согласованность

Операции изменения данных выполняются в локальных транзакциях соответствующего сервиса. Операции чтения, где это возможно, помечены как `readOnly`.

При создании заказа `order-service` вызывает `product-service` и `inventory-service` через Feign. Распределённая транзакция не используется: если резервирование одной позиции завершилось ошибкой, сервис освобождает резервы, созданные для предыдущих позиций. При деградации зависимых сервисов заказ сохраняется в статусе `PENDING_CONFIRMATION`.

## Конфигурация и обнаружение сервисов

`discovery-server` запускается на порту `8761` и не регистрирует себя как Eureka Client.

Остальные приложения регистрируются в Eureka. Commerce-сервисы и Config Server используют динамические HTTP-порты, поэтому вызывающие сервисы находят их по имени, а не по фиксированному адресу.

`config-server` работает с профилем `native`. Конфигурации приложений хранятся внутри его classpath:

```text
infra/config-server/src/main/resources/config-repo/telemetry/{application}/
infra/config-server/src/main/resources/config-repo/commerce/{application}/
```

После изменения этих файлов Config Server необходимо пересобрать и перезапустить, иначе новая конфигурация не попадёт в `target/classes`.

Клиенты используют fail-fast и повторные попытки загрузки конфигурации. Поэтому порядок запуска инфраструктуры важен:

1. `discovery-server`;
2. `config-server`;
3. прикладные сервисы.

## Логирование и наблюдаемость

Во всех запускаемых Spring Boot-сервисах подключён Actuator. Проверка состояния доступна по стандартному адресу:

```text
/actuator/health
```

В товарных сервисах логирование сосредоточено на уровне бизнес-операций:

- `DEBUG` — чтение данных, параметры выборки и межсервисные проверки;
- `INFO` — успешное создание и изменение сущностей;
- `WARN` — ожидаемые бизнес-отказы, например нехватка товара или отсутствие позиции в корзине;
- `ERROR` — необработанные технические ошибки.

Большие коллекции и полные DTO намеренно не записываются в журнал.

## Обработка ошибок

Commerce-сервисы используют собственные обработчики исключений и единый формат тела ошибки. Отдельно обрабатываются:

- ошибки валидации запроса;
- отсутствующие товары, остатки и заказы;
- недостаточное количество товара;
- конфликты при создании или изменении складских записей;
- ограничения базы данных;
- неожиданные внутренние ошибки.

Ожидаемые бизнес-ошибки не маскируются общим ответом `500`.

## Сборка

Требования:

- Java 21;
- Maven 3.9+;
- Docker Compose для Kafka;
- PostgreSQL.

Сборка всех модулей выполняется из корня проекта:

```bash
mvn clean verify
```

Для запуска Kafka и создания топиков:

```bash
docker compose up -d
```

В локальном PostgreSQL должны существовать отдельные базы сервисов. Параметры подключения задаются в конфигурациях Config Server.

Пример подготовки окружения разработки:

```sql
CREATE USER dbuser WITH PASSWORD '12345';

CREATE DATABASE telemetry_analyzer OWNER dbuser;
CREATE DATABASE product_db OWNER dbuser;
CREATE DATABASE inventory_db OWNER dbuser;
CREATE DATABASE order_db OWNER dbuser;
```

## Рекомендуемый порядок запуска

1. PostgreSQL и Kafka.
2. `discovery-server`.
3. `config-server`.
4. `collector`, `aggregator`, `analyzer`.
5. Тестовый Hub Router при проверке сценариев автоматизации.
6. `product-service`, `inventory-service`, `order-service`.
7. `api-gateway`.

После запуска прикладные сервисы должны отображаться в Eureka со статусом `UP`.
